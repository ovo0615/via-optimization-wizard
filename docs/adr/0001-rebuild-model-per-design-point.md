# 每個設計點重建模型，而不是參數化 AEDT 變數

最佳化迴圈裡改變幾何，正常做法是在 AEDT 裡建一次帶變數的模型，之後只餵新的變數值讓 AEDT 自己重算幾何。我們**不走這條路**：每個設計點都從模型描述（JSON）完整重建一個新的 `.aedb`。

原因是建模器（fork 自 Via Wizard 的 `modeling.py`）把幾何值烘死成數字字串——`f'{holeDiameter}{units}'`——而且差分對的 P/N 位置是在 Python 端用 `pitch / 2` 算完才交給 EDB 的。要改成吃 AEDT 變數，等於要把整個建模器的座標運算搬進 AEDT 的運算式系統重寫，而那正是這份程式碼已經驗證過、我們最不想動的部分。

代價可以接受：重建一個 `.aedb` 只要幾秒，HFSS 求解才是分鐘級的瓶頸。

## Consequences

- **模型描述是唯一的真相來源。** 設計變數必須是模型描述裡的欄位，不能是 AEDT 裡的變數。新增一個設計變數＝在模型描述裡多開一個欄位並確認建模器讀得到它。
- **求解器介面天然成立。** 既然每個設計點的輸入就是一份完整的模型描述、輸出就是一組響應，換成預跑查表或未來的 SimAI 只是換一個實作，不必動最佳化那一端。
- **裁切下來的真實幾何不能當最佳化對象。** 從客戶 `.aedb` 裁出來的是實體多邊形，沒有「這個 antipad 是設計變數」的語意，無法重建。所以專案模式只吃模型描述；客戶板子的貢獻限於疊構讀取。
- **每個設計點需要自己的工作目錄。** 平行跑時各自建各自的 `.aedb`，彼此不能共用路徑。建模器結尾的 `os._exit(0)` 也因此必須以 subprocess 隔離呼叫，不能 import 進來直接跑。
